# 06. Техническое задание на разработку

---

## 1. Цель и измеримые результаты

**Цель:** сайт, который приводит квалифицированные B2B-заявки на регулярное
обслуживание коммерческих объектов в Екатеринбурге.

**KPI на 6 месяцев после запуска** (базу зафиксировать до старта работ):

| Метрика | Целевое значение |
|---------|------------------|
| Индексация | 100 % страниц в индексе Яндекса |
| Позиции по 10 ключевым запросам | топ-10 в регионе |
| Конверсия в заявку (весь сайт) | не менее 2,5 % |
| Конверсия страниц услуг | не менее 4 % |
| Доля мобильного трафика с заявками | не менее 40 % от общего числа |
| Core Web Vitals (мобильные) | LCP < 2,5 с, INP < 200 мс, CLS < 0,1 |
| Отказы | менее 35 % |
| Доля заявок с определённым источником | 100 % (UTM + коллтрекинг) |

## 2. Выбор платформы

Три реалистичных варианта. Ключевой фактор — кто будет поддерживать сайт после
запуска.

### Вариант A. Конструктор (Tilda и аналоги)
- **Плюсы:** быстро, дёшево, редактируется без разработчика, приличная скорость.
- **Минусы:** ограничения по микроразметке и техническому SEO, сложно сделать
  нестандартный калькулятор, абонентская плата, привязка к платформе.
- **Кому:** если нет бюджета на поддержку и нужно запуститься за 3–4 недели.

### Вариант B. CMS (1С-Битрикс, ModX, WordPress) — рекомендуемый
- **Плюсы:** полный контроль над SEO и разметкой, любой функционал,
  привычная админка, легко найти подрядчика в Екатеринбурге, интеграции с 1С
  и Битрикс24 из коробки.
- **Минусы:** дороже, требует внимания к скорости и безопасности.
- **Кому:** основной сценарий для этого проекта. 11 посадочных, блог, кейсы,
  калькулятор, интеграция с CRM — это уже полноценный сайт, а не лендинг.

### Вариант C. Next.js / Astro + headless CMS
- **Плюсы:** максимальная скорость, лучшие показатели Core Web Vitals.
- **Минусы:** нужен фронтенд-разработчик на поддержке, дороже, дольше.
- **Кому:** если планируется развивать сайт как основной канал продаж.

**Рекомендация:** вариант B. При этом текущий сайт, судя по домену
`hcln.test-1pos.ru`, сделан на платформе-конструкторе — перед выбором нужно
выяснить, кто владеет исходниками и есть ли доступ к экспорту контента.

**Что бы ни выбрали — обязательные требования одинаковы:** пункты разделов 3–10
ниже входят в приёмку.

## 3. Вёрстка и фронтенд

- Семантический HTML5: `header`, `nav`, `main`, `section`, `article`, `footer`.
- **Валидность по W3C.** В текущем коде: `div` внутри `ul`, вложенные `<p>`,
  `lang="en"` — не повторять.
- Адаптив: 360, 390, 768, 1024, 1280, 1440, 1920. Проектирование от мобильного.
- `<meta name="viewport" content="width=device-width, initial-scale=1">` —
  **без `maximum-scale`**.
- Кроссбраузерность: Chrome, Safari, Firefox, Edge — две последние версии;
  Яндекс.Браузер; iOS Safari 15+.
- Никакого jQuery. Slick и Fancybox заменить на нативные решения:
  CSS scroll-snap для каруселей, `<dialog>` для модальных окон.
- CSS: кастомные свойства для токенов из файла 07, вложенность селекторов
  не глубже 3 уровней, никаких `!important` кроме утилит.
- Доступность: контраст текста не ниже 4.5:1, видимый фокус клавиатуры,
  все интерактивные элементы достижимы с клавиатуры, `prefers-reduced-motion`
  уважается, формы с `<label>`.

## 4. Производительность

Целевые значения на мобильном при медленном 4G:

| Показатель | Цель |
|-----------|------|
| LCP | < 2,5 с |
| INP | < 200 мс |
| CLS | < 0,1 |
| Вес первого экрана | < 500 КБ |
| Общий вес страницы | < 1,5 МБ |
| PageSpeed Insights (mobile) | ≥ 85 |

Обязательные меры:
- изображения в WebP/AVIF с JPEG-фолбэком, через `<picture>` и `srcset`;
- `loading="lazy"` на всё ниже первого экрана, `fetchpriority="high"` на
  главное изображение первого экрана;
- явные `width` и `height` у всех изображений (иначе скачет CLS);
- **имена файлов латиницей** — текущие кириллические URL-кодированные имена
  типа `%D0%A3%D0%B1%D0%BE%D1%80%D0%BA%D0%B0...` переименовать;
- шрифты: `font-display: swap`, подгружаются только нужные начертания,
  формат woff2, `preload` для основного;
- сторонние скрипты (Метрика, виджеты отзывов, коллтрекинг) — отложенно,
  виджет отзывов подгружается при попадании в область видимости;
- HTTP/2 или HTTP/3, gzip/brotli, кеширующие заголовки на статику;
- критический CSS инлайном, остальной — отложенно.

## 5. Формы и лидогенерация

### Общие требования ко всем формам
- Минимум полей: имя + телефон. Всё остальное — опционально.
- Маска и валидация телефона, `inputmode="tel"`.
- **Отдельный чекбокс** согласия на обработку персональных данных со ссылкой
  на страницу политики (не попап). Незаполненный чекбокс блокирует отправку.
- Защита от спама: honeypot + ограничение частоты отправок с одного IP +
  Яндекс SmartCaptcha при подозрении. Обычную капчу для всех не ставить —
  режет конверсию.
- Автоподстановка UTM-меток и `referrer` в скрытые поля. **В текущем коде
  поля есть, но пустые — это главная причина, почему источник заявок неизвестен.**
- Скрытое поле с URL страницы, с которой отправлена заявка.
- Состояния: загрузка, успех, ошибка. Тексты — из файла 04.
- Отправка без перезагрузки страницы, дублирование в Telegram-чат менеджеров.

### Набор форм
1. Быстрая заявка в шапке — «Заказать КП»
2. Калькулятор → «Уточнить и получить КП»
3. Форма на каждой странице услуги
4. Финальная форма — «Вызвать специалиста на объект»
5. Обратный звонок с выбором удобного времени
6. Форма с загрузкой файла (план помещения, техзадание для тендера) —
   ограничение по типу и размеру, проверка на сервере

### Калькулятор — отдельное требование
- Шаги: тип объекта → вид уборки → площадь → частота → допуслуги.
- **Результат выводится до запроса контактов**, в виде диапазона.
- На мобильном — пошаговый режим, один вопрос на экран, индикатор прогресса.
- Формула и коэффициенты редактируются из админки без программиста.
- Каждый шаг отправляет событие в Метрику — видно, где отваливаются.

## 6. Интеграции

| Система | Назначение | Приоритет |
|---------|-----------|-----------|
| CRM (Битрикс24 или amoCRM) | Все заявки в воронку с источником | Обязательно |
| Telegram-бот | Мгновенное уведомление менеджеру | Обязательно |
| Яндекс.Метрика | Аналитика, цели, Вебвизор | Обязательно |
| Коллтрекинг (Calltouch, Roistat, Comagic) | Атрибуция звонков — в клининге это большая часть обращений | Обязательно |
| Email-рассылка | Отправка КП, догрев | Желательно |
| Виджет Яндекс.Карт | Отзывы и адрес | Желательно |
| ЭДО | Упоминание на сайте, интеграции не требует | — |

**Не устанавливать:** Google Universal Analytics (прекратил работу в 2023 году,
сейчас висит в коде мёртвым грузом), любые виджеты запрещённых в РФ платформ.

## 7. Аналитика: что настроить

**Яндекс.Метрика:**
- `webvisor: true`, карта скроллинга, карта кликов;
- цели: отправка каждой формы (отдельно по типу), клик по телефону,
  клик по Telegram/WhatsApp, завершение калькулятора, скачивание договора
  и техкарты, глубина просмотра 75 %;
- составные цели для воронки калькулятора (шаг 1 → шаг 5 → заявка);
- электронная коммерция для оценки ценности заявки (опционально);
- связка с Директом и целевой звонок из коллтрекинга.

**Обязательное правило:** ни одна форма не публикуется без настроенной цели.
Форма без цели — это заявки, о которых никто не знает.

## 8. Микроразметка

Реализовать через JSON-LD (не микроданные в атрибутах — их сложнее поддерживать).

Обязательный набор: `Organization`, `LocalBusiness` (с `address`, `geo`,
`openingHours`, `telephone`, `priceRange`), `BreadcrumbList`, `Service` на
страницах услуг, `FAQPage` на главной и страницах услуг, `ImageObject` в галерее.

Убрать текущий `Product` с пустой ценой.

## 10. Хостинг, безопасность, эксплуатация

- Хостинг в РФ, SSL с автопродлением, HTTP/2+.
- Автоматические резервные копии: ежедневно, хранение 30 дней, проверенное
  восстановление.
- Разделение контуров: боевой и тестовый. **Тестовый закрыт HTTP-авторизацией**
  (не robots.txt — так, как сейчас, не работает).
- Никаких кросс-доменных ссылок на статику: боевой сайт грузит ресурсы только
  со своего домена. Сейчас — 163 обращения к тестовому домену.
- Мониторинг доступности с уведомлением в Telegram.
- Регулярное обновление CMS и модулей.
